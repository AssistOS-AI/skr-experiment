# Runtime and session contract

The Node.js 24 server binds to `127.0.0.1` by default. Run `npm start`, create the first account using the owner-only one-time bootstrap token in `data/auth/bootstrap.token`, then sign in through the app. Subsequent accounts are manager-created. Project, source, run, explain, fork, rebase, publication, skill, procedure, and entity operations are checked against project capabilities. Sessions expire after eight idle hours and logout revokes the current bearer token. The optional `SKR_TRUSTED_LOCAL=1` startup mode bypasses authentication and is only for explicitly trusted local development. It is not enabled by default.

The production coding adapter is fixed to `codex exec --model gpt-6-luna`. Neither request fields nor project configuration can select a different executable, provider, or model. Codex user config/rules and known backend-override environment variables are excluded, while the authenticated local CLI credentials are copied into a private per-run `CODEX_HOME`; credentials and raw rollouts are never included in exported reports. No alternate model or backend fallback runs if Codex fails. The deterministic reference runner is available only when explicitly selected for a demo or test and its execution metadata is labeled `reference`.

Each run pins an immutable snapshot, the authorized source-version scope, the exact skill bundle and digest, and any selected procedure ID/version and parameters. Workspaces contain a server-written request and filtered snapshot, the selected source originals, only the approved skill versions, and separate `work`, `state`, `out`, and `events` directories. Codex runs inside a fail-closed Bubblewrap namespace: pinned snapshot, sources, skills, and runtime inputs are read-only; only run scratch and staged output are writable; host `/tmp` and unrelated home directories are not mounted. If required namespace isolation cannot start, the run fails instead of retrying unsandboxed. Environment variables passed to the coding subprocess are allow-listed; unrelated service secrets are not inherited.

Codex session UUIDs, cumulative raw usage, per-turn usage deltas, checkpoints, and request counts are persisted under the run's private session directory. A resumed run keeps its original run ID, workspace, snapshot, source scope, skills, and Codex conversation. Server restart marks active work interrupted; publication uncertainty is never silently retried. Cancellation reaches active model requests and terminates their process group; once the atomic publish phase begins, cancellation is rejected.

The six task handlers are `QUESTION`, `INGEST_SOURCE`, `APPLY_PROCEDURE`, `BUILD_PROCEDURE`, `AUDIT_PROJECT`, and `EVALUATE`. Source upload registers immutable original bytes and regions; semantic ingestion is a separate task. Ingestion assertions and procedure findings are reviewed in an independent Luna turn and accepted only with server-side receipts bound to the exact source passage, qualifiers, procedure, and session. A question can resolve against temporary reviewed assertions without committing them; the server persists the validated run-local evidence context for later audit/replay. Prose without successful review stays staged or unresolved. Questions default to no analysis procedure. Selected procedures must match an active, exact pinned version; authored drafts remain inactive until a manager approves that immutable version. A procedure may explicitly opt into `on-ingestion` materialization with concrete pinned parameters; after manager approval, it runs within the source-ingestion transaction and publishes its reviewed findings with the other validated ingestion changes. All other methods remain explicit; no background source-update scheduler is implied.

Run output is validated against the authoritative in-memory pinned snapshot and source scope before it is exposed or committed. Source quotes must reopen in the exact region; derived claims must replay from authorized premises; procedure reports must cite exact supporting and counterevidence. Evidence integrity by itself does not establish entailment, so support state, audit result, coverage, and unresolved residuals remain explicit. Changes are staged by default. A project policy may allow selected task types to publish automatically; a manager may also publish a validated staged change if the snapshot has not changed.

Key routes include account bootstrap/login/logout/user creation, project and member management, scoped source upload/inspection/original download, project export, fork/rebase, skill request/approval/link, exact-version procedure approval, entity merge/undo, run creation/status/explain/resume/cancel/publish, and policy update. Mutating browser requests require same-origin JSON and cross-site fetches are rejected. The API and UI are single-user-on-loopback oriented; this configuration is not a public deployment with network identity or remote access controls.

The checked-in Codex output schema is in `src/runtime/output-schema.json`. Strict JSON transport fields for bindings, scope, coverage, validation, and changes are decoded and checked before normalization. The workspace `out/` bundle is server-owned publication output, not a trust source. Evaluation artifacts retain only sanitized summaries; do not export a private Codex home, auth material, or raw session logs.
